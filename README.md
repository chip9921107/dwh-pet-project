\# Учебный DWH: от грязных данных до аналитической витрины



Pet-проект, демонстрирующий полный цикл построения корпоративного хранилища данных (DWH)

на примере агрохолдинга с розничной сетью: от сырых данных из кассовой системы

до аналитической витрины в ClickHouse.



\## Архитектура



Staging (PostgreSQL) → Core (PostgreSQL) → Mart (ClickHouse)

&#x20;  грязные данные      очистка, SCD2,        денормализация,

&#x20;                      звёздная схема       партиционирование



\- \*\*Staging\*\* — сырые данные «как пришли»: даты в трёх форматах, пробелы, `NULL`, дубли.

\- \*\*Core\*\* — очищенные данные: приведение типов, дедупликация, справочники (`dim\_\*`),

&#x20; таблица фактов (`fact\_sales`), SCD Type 2 для истории изменений товаров.

\- \*\*Mart\*\* — денормализованная витрина в ClickHouse (`MergeTree`, `PARTITION BY toYYYYMM`,

&#x20; `ORDER BY`), оптимизированная под аналитические запросы.

## Модель данных (Core)



| Таблица | Тип | Описание |

|---|---|---|

| `core.dim\_date` | измерение | Календарь 2024 года (366 дней) |

| `core.dim\_store` | измерение | 10 магазинов, очищенные названия и города |

| `core.dim\_product` | измерение (SCD2) | 50 товаров + 10 исторических версий, `valid\_from`/`valid\_to`/`is\_current` |

| `core.fact\_sales` | факт | 100 000 продаж, внешние ключи на измерения |

| `core.sales\_denorm` | view | Денормализованное представление для загрузки в Mart |



\## Контроль качества данных



В проекте реализованы и проверены:



\- \*\*Целостность\*\*: 0 «сирот» в `fact\_sales` (все ключи находятся в измерениях).

\- \*\*Очистка дат\*\*: три формата (`YYYY-MM-DD`, `DD.MM.YYYY`, `DD/MM/YYYY`) приведены к `DATE`, 0 некорректных дат.

\- \*\*SCD Type 2\*\*: у каждого товара ровно одна текущая версия (`is\_current = true`).

\- \*\*Согласованность Core ↔ Mart\*\*: сумма продаж совпадает до копейки (44 182 568.00).

\- \*\*Осознанная фильтрация\*\*: из 100 000 фактов в витрину попало 83 917 — отфильтрованы

&#x20; 16 083 строки с `NULL` в количестве или сумме (для аналитики продаж они бессмысленны).

## Обнаруженные и исправленные проблемы



1\. \*\*Потеря строк при JOIN в ClickHouse.\*\* При загрузке Mart через три отдельных

&#x20;  `postgresql()`-источника ClickHouse терял часть строк. Решение: вынести JOIN

&#x20;  в PostgreSQL View (`core.sales\_denorm`) и читать в ClickHouse одну готовую таблицу.

2\. \*\*Две текущие версии в SCD2.\*\* У двух товаров дубли не меняли цену, и `UPDATE`

&#x20;  не закрывал старую версию. Решение: пересобрать `dim\_product` с `ROW\_NUMBER()`

&#x20;  по `valid\_from DESC`, чтобы текущей всегда была только последняя версия.



\## Запуск



1\. Поднять контейнеры:

&#x20;  `docker compose up -d`



2\. Выполнить SQL-скрипты по порядку:

&#x20;  `docker exec -i dwh-postgres psql -U postgres -d dwh -f /sql/01\_staging.sql`

&#x20;  `docker exec -i dwh-postgres psql -U postgres -d dwh -f /sql/02\_staging\_data.sql`

&#x20;  `docker exec -i dwh-postgres psql -U postgres -d dwh -f /sql/03\_core.sql`

&#x20;  `docker exec -i dwh-clickhouse clickhouse-client --multiquery --queries-file /sql/04\_mart\_clickhouse.sql`

## Подключение через DBeaver



\- \*\*PostgreSQL\*\*: `localhost:5432`, БД `dwh`, пользователь `postgres`, пароль `postgres`.

\- \*\*ClickHouse\*\*: `localhost:8123`, БД `mart`, пользователь `admin`, пароль `admin123`.

&#x20; Если возникает ошибка `Invalid LZ4 magic byte`, в настройках драйвера установите `compress=false`.



\## Навыки, продемонстрированные в проекте



\- Проектирование слоёв DWH (Staging / Core / Mart).

\- Нормализация, очистка и контроль качества данных.

\- Размерное моделирование: звёздная схема, измерения, факты.

\- SCD Type 2 (история изменений).

\- PostgreSQL: оконные функции, `FILTER`, `DISTINCT ON`, View.

\- ClickHouse: `MergeTree`, партиционирование, ключ сортировки, чтение из PostgreSQL.

\- Docker / Docker Compose: изоляция сервисов, volumes, сети.

\- Диагностика расхождений в данных и объяснение результатов.
